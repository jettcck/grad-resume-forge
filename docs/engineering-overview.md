# 工程概览 · Grad Resume Forge

> 这份文档面向**代码评审与技术面试**，说明架构怎么分层、关键决策为什么这么定、
> Agent 部分怎么自证有效，以及哪些地方**还没做**。
>
> 产品功能与安装方式见 [README](../README.md)。

---

## 1. 一句话定位

本地优先的求职桌面端：**一个可控的 LLM Agent** 负责把真实经历改写成不像 AI 写的简历要点，
**一套确定性引擎**负责审计、打分与防幻觉校验；另有客观题/编程题笔试中心与投递管理。
无模型也能用（规则引擎兜底），有模型则更自然——**AI 是可选增强，不是前置依赖**。

## 3. 三个关键决策（都带代价）

### 3.1 为什么把 Agent 运行时抽成独立包

原来 Agent 流程是一段 `for` 循环：能跑，但答不出「现在跑到哪一步、能不能取消、失败停在哪、上次为什么拒了这条」。

抽出来之后 core 只管状态推进 / 工具调度 / 预算 / trace / 回放，业务语义留在 `src/main/agent.ts`。

**代价**：多一层抽象与依赖注入，改一个工具要动两个地方。**收益**：core 能在无 Electron、无业务数据下测试与回放——这是后面一切可观测性的前提。

### 3.2 为什么状态机要抛错，而不是一路放行

```
CREATED → ANALYZING_JD → PLANNING → EXECUTING_TOOLS → VALIDATING → CRITIC_REVIEW → COMPLETED
                                    ↕                    ↕              ↕
                            WAITING_HUMAN_APPROVAL   PARTIAL      FAILED / CANCELLED
```

11 个状态（7 非终态 + 4 终态），用一张**允许转移表**约束推进，非法转移直接抛错。

开发中撞到过一次 `VALIDATING → COMPLETED` 漏配：运行时抛错 → 整次运行判失败。如果当时选择放行，这类错误会以「界面状态显示不对」的形式**悄悄漏到用户那边**。

**代价**：每次加状态要同时改表与测试。**收益**：状态错误在开发期暴露，不会变成用户侧的诡异现象。

### 3.3 为什么只有幂等工具才自动重试

工具契约里 `idempotent` 是必填项：

```ts
{ name, description, inputSchema, permission: 'readonly' | 'write',
  timeoutMs, maxRetries, idempotent, execute(args, ctx) }
```

非幂等的写操作重试可能造成重复写入，所以**宁可失败让上层决策**。

配套的取舍：
- 超时用 `Promise.race` 而不是真打断——JS 没有抢占，底层调用打断不了；**文档里写明「不能 kill」，不假装能**
- 入参校验放在运行时——模型给什么形状都有可能（benchmark 有专门的 `bad_args` 用例）
- 预算超限返回错误而不是抛异常——让模型有机会收工并如实交代

## 4. Agent 能做什么（6 个工具）

| 工具 | 权限 | 作用 |
|---|---|---|
| `analyze_jd` | readonly | 从 JD 抽技能关键词、判断岗位方向 |
| `audit_text` | readonly | 对当前简历做确定性体检（套话、弱动词、量化占比） |
| `llm_rewrite` | readonly | 调模型产出候选改写（**不直接写档案**） |
| `rewrite_bullets` | write(候选取) | 规则层改写，产出候选进 `ctx.accepted` |
| `validate_rewrites` | readonly | 校验门：数字必须保全、不许出现档案里没有的技能 |
| `submit_result` | write | 收工，附完成度与自评 |

**Agent 没有无约束写权限**：所有改写只是候选，过校验门后进入 `ctx.accepted`，
真正写入档案必须用户在界面点「应用」。这是产品决策，也是安全边界。

## 5. 可观测性与脱敏

每条运行记录：`runId / taskId / status / currentStep / inputSnapshot / budget / usage / trace`。
trace 每步记 `tool / 输入摘要 / 输出摘要 / latencyMs / retryCount / tokens / errorType`。

**脱敏是白名单式替换，不是截断**：

| 项 | 处理 |
|---|---|
| 输入快照 | 只有条目数、分节计数、JD 长度与指纹、档案指纹；不含姓名与正文 |
| trace 入参 | 超 **12 字**的字符串 → `{len, digest}`；条目 id、工具名等短标签保留 |
| trace 出参摘要 | **走同一条规则**（只脱敏入参不够，出参同样会带出原文） |
| 记录文件 | 按账号分文件 `agent-runs-<userId>.jsonl` |
| API Key | 这一层根本拿不到 |

12 字这个阈值是被测试反推出来的：第一版定 24 字，被一条 18 字的改写用例证伪——真实简历要点普遍 15–40 字，24 字等于一半内容照样落盘。

默认不存原文，所以「按记录完整回放」需要显式开启 `storeTraceArgs`；默认回放会**如实报告**「有 N 步因未保存入参被跳过」，而不是拿占位对象跑出一堆假错误。

## 6. 评测体系（怎么自证有效）

### 6.1 mock 层（进 CI，零模型成本）

`evals/agent-bench.js`：65 个任务用例，用**真实** `agenticLoop` + 真实校验门，只把模型换成脚本化 mock。

| 类别 | 用例数 | 考察点 |
|---|---|---|
| happy | 7 | 正常完成（分析→改写→体检→收工） |
| no_analysis | 7 | 跳过 JD 分析：critical 缺失应被催，并如实标注 |
| lazy | 7 | 一上来就收工：催 2 次后如实收工，不许假装成功 |
| partial | 7 | 一条过门、一条改数字被拒 |
| all_rejected | 7 | 全部被拒 → 不算成功 |
| bad_args | 7 | 模型给错参数形状 → 运行时校验拦下且能继续 |
| unknown_tool | 7 | 调用不存在的工具 → 白名单拦下 |
| injection | 7 | JD 里夹带指令诱导编造技能 → 防幻觉门拦住 |
| no_metrics / long / empty | 9 | 无量化的简历、20 条超长简历、空档案 |

**实测基线**（`node evals/agent-bench.js`，确定性，可复现）：

```
行为符合预期      100%   ← 门禁用这个：该成功就成功、该失败就失败
业务完成率        63.1%  （41/65 真正 ok=true；失败样本按设计不完成）
干净路径成功率    100%   （89 次调用，不含注入失败）
工具调用成功率    89.3%  （131 次，含故意注入的失败）
改写通过率        87.2%  （通过 143 / 拒收 21）
数字保全率        100%
编造技能率        0%
运行时开销均值    1.7ms  （不含模型推理：mock 不产生真实延迟）
```

**为什么要有两个口径**：上一版只报「任务成功率 100%」，但把「没分析 JD 却有一条改写」的用例期望写成了 `ok: true`——等于把业务没做完算成成功。现在分开：**行为符合预期**衡量「该成功就成功、该失败就失败」，**业务完成率**衡量真正完成的比例。

### 6.2 真实模型层（需端点，不配则明确跳过）

`evals/agent-bench-llm.js` 支持 Ollama / OpenAI 兼容端点，**没配就打印跳过、不编数字**。

它带一个 `--self-test`：本地起一个 OpenAI 兼容的假服务，走完同一条代码路径并硬断言「请求发得出去、工具调用解析得回来、指标能汇总」。这条自测第一次跑就抓到一个真问题：假服务用 OpenAI 协议，而客户端在无 apiKey 时按 Ollama 协议发请求，于是解析不到工具调用。

### 6.3 两个真实结论（含一个负结果）

**负结果一：1.5B 级模型驱动不了 Agent。**

用 `qwen2.5:1.5b` 通过 Ollama 的 OpenAI 兼容端点跑本评测：**任务完成率 0%，且模型全程不产生 `tool_calls`**（返回空 content、`finish_reason=stop`）。

这不是框架问题——同一端点用最小请求验证过 `tools` 参数能正常收发（普通对话正常返回，带 tools 的请求返回 200 但无 tool_calls）。结论是 **Agent 任务对模型规模有下限**：1.5B 级模型无法稳定驱动多轮工具调用。

这类负结果照样值得记录：它证明评测能区分「框架坏了」和「模型不行」。

**未完成项：7B 的正向指标（环境限制，非能力限制）。**

`qwen2.5:7b`（4.7GB）在本机沙箱环境中未能完整拉取：单条命令有执行时长上限，
而 Ollama 的 blob 下载在中断后会丢弃临时分片、从头重下（实测第二次 pull 的 `completed`
从 2.08GB 回落到 0.97GB）。**这不是代码问题**，在正常网络下的复现方式是：

```bash
# 一次连续执行（约 30–45 分钟，取决于带宽）
ollama pull qwen2.5:7b
set AGENT_BENCH_ENDPOINT=http://127.0.0.1:11434/v1
set AGENT_BENCH_MODEL=qwen2.5:7b
node evals/agent-bench-llm.js --sample 20
```

记录指标时请同时写明**模型、参数、用例数**三件套（例如 `qwen2.5:7b / temp 0.2 / 20 用例`），
否则数字不可比。

## 7. 判题沙箱（另一个隔离面）

43 道编程题 × JS / Python / C++，207 条断言守着：

- **编译一次、多用例复用**；`g++ -O2 -std=c++17 -static`（`-static` 免 DLL 依赖）
- 超时 / 超限用 `taskkill /PID <pid> /T /F` 杀**整棵进程树**，避免孤儿进程烧 CPU
- 输出超 64KB 判 OLE 并截断；编译错误原样回传（含行号）判 CE
- 实测踩坑：Windows Defender 扫描新编译的 exe，冷启动可达 1.6s，按 1000ms 硬卡会把正确程序误判 TLE；且扫描有时直接杀进程表现为 RE。对策是 **1.5s 启动宽限 + RE 自动重试一次**（真崩溃仍崩，误杀则恢复）

## 7.5 PDF 简历导入：三个不显眼但影响很大的点

导入链路用 `pdfjs-dist` 抽文本，再走规则解析。三处设计值得说明：

**1. 不依赖 `hasEOL`，按坐标聚行 + 中缝检测**

`hasEOL` 来自 PDF 内容流的换行标记，在双栏 / 表格 / 分块排版里完全不可靠——
左右栏的文本项按内容流顺序交错。

第一步：按 `textItem.transform` 的 y 坐标聚行（容差取常见字号的 60%，夹在 2–6pt），
行内按 x 排序、片段间有明显间隙才补空格。
细节：`张三` 和 `13800000000` 紧邻时不硬插空格，否则手机号正则的边界判断会失效。

第二步（更关键）：**只按 y 聚行仍然会把左右栏同一高度的两行拼在一起**。
实测双栏样本会出现「教育背景 实习经历」「浙江大学 本科 阿里巴巴 后端」这种串行。
所以要检测中缝，然后**先读完左栏再读右栏**。

中缝检测踩了三层坑，每一层都是被样本测出来的：

1. **不能用「中部有没有字形」判**。侧边栏模板顶部是通栏的姓名与联系方式，
   横跨中缝所在的 x 区间，于是「中部有字」成立 → 检不出分栏。
   改成按**垂直空白覆盖率**：统计每个 2px 横向区间被多少行占用，
   覆盖率 ≤ 25% 才算空白带。顶部两行通栏只会让中缝覆盖率变成 2/16 = 12.5%，仍能检出。
2. **搜索区间不能用「页宽的 30%–70%」**。简历正文往往只占页宽一半，右侧大块空白
   也是覆盖率 0，会被当成中缝（实测检出了 x=367 的假中缝，真栏缝在 180 附近）。
   改成用**内容实际 x 跨度**的中点 ±25%。
3. **还要确认两侧都有实质内容**。ATS 简历常见「正文 + 右侧日期列」，
   右侧只占 9% 文字量——那不是分栏，按它分会把日期和正文拆散。
   加判据：较小一侧的字符占比 ≥ 25%（实测：日期列 9%、真双栏 40%、侧边栏 60%）。

单栏不会误判：正文横跨整页，中部没有长空白。已在 3 份单栏 + 1 份双栏 + 1 份侧边栏样本上验证。

**行内拆分的两个细节**：
- 一行左右各有内容时（`专业技能 | 教育背景`），必须拆成两条分别进左右缓冲。
  早期版本按「多数派」整行归边，会把另一栏的文字一起带过去。
- pdfjs 的一个 `item` 可能是一整行文字，跨中缝时要按字符切；
  **只在切点附近 ±1 字符恰好是空格时才切**，否则整行不拆——
  放宽到 ±4 会把联系方式从词中间劈开（`13700000000 · wangw` / `u@example.com …`）。

修复前后对比：双栏样本 13 行 → 18 行，侧边栏样本 16 行 → 19 行，串行行全部消失。

**2. 全角字符只转该转的**

中文简历里「２０２２」「Ｊａｖａ」「ｌｉｓｉ＠ｅｘａｍｐｌｅ．ｃｏｍ」很常见，
不转的话年份、技术栈、邮箱正则全部匹配不上。

转的范围是 `[０-９ Ａ-Ｚ ａ-ｚ]` 加 `＠．－／`，**刻意不转全角冒号「：」**——
它在中文正文里高频（`姓名：张三`），转成半角会让界面上的标点风格不统一，
而邮箱格式本来就用不到冒号。第一版把冒号一起转了，被一条「作品集：财务分析报告」的用例抓出来。

**3. 页码噪声只认「整行就是页码」**

多页简历每页都带「第 1 页 / 共 2 页」「Page 1 of 2」「- 3 -」，混进来会破坏分节判定。
但过滤必须保守：只匹配整行，否则「专业排名 1/2」这类正文会被误删。
正则里有个容易漏的形态——「第 1 页 / 共 2 页」中间那个「共」，
第一版写 `[/／共]` 结果斜杠后的「共」匹配不上，测试直接暴露。

另外：抽取到的有效文本少于 20 字时直接报错「可能是扫描件 / 图片版」，
而不是返回一个空结果让用户以为解析失败。

**4. 表格与多页**

表格不必特殊处理：**一行单元格的文本在同一视觉基线上，按 y 聚行自然就拼成一行**
（`Java 精通 3 年`），这正好是表格行该有的形态。但要注意它不能把分节搞乱——
技能表落在「专业技能」之后、获奖表落在「获奖情况」之后，靠的是分节标题的顺序，与表格无关。

多页有两个坑：

- **页码行会被当成正文**。已有 `stripPageNoise` 过滤「第 1 页 / 共 2 页」「Page 1 of 2」「- 3 -」「1/2」，
  但只匹配「整行就是页码」——否则「专业排名 1/2」会被误删。
- **跨页时分节不能重新开始**。第 2 页接着上一页写实习内容时，段落属于同一节，
  不该因为换页就新开一条。实测两页样本：实习仍是 1 段、项目 1 段。

造多页样本时踩了一个坑：**靠「内容溢出」自动分页不可靠**，`printToPDF` 会按纸张缩放，
36 行内容仍挤在一页。改用显式 `page-break-after: always` 才稳定复现。

**5. 两个容易误分类的启发式**

- **列表编号 vs 年份**：`BULLET_RE` 原本是 `^\d+[.、)]`，会把 `2021.07 - 2021.12` 的 `2021.`
  当成列表编号剥掉，于是时间行被判成项目符号行、跳过了「补 period」的分支，
  整条时间被塞进描述。收紧成 `^\d{1,2}[.、)]`（列表编号很少超过两位）。
- **动词开头的描述 vs 条目名**：`looksLikeTitle` 靠关键词命中（公司/开发/实习…），
  于是「参与基站配置管理系统的模块开发」因为含「开发」被当成新条目，
  把一段实习切成两段。加一条：以「参与/负责/协助/完成…」开头的行不算标题。

## 8. 测试

```
32 个测试文件 / 1,652 条断言
npm test   # 含 evals：mock 层评测 + LLM 层 self-test + 规则层评测
```

分层：
- **纯函数层**：`exam-core`、`resume-engine`、`agent-core`（可脱离 Electron）

- **真实 UI**：CDP 驱动打包版应用，断言 DOM 与交互（不依赖人工点）

| **检索层未接入组卷** | `packages/retrieval` 已实现 BM25 / 向量 / RRF 并做了 20 条标注评测（见 [retrieval.md](retrieval.md)），但 `buildPaper` 仍用 tag 精确匹配——换检索需要重新验证组卷质量，属于下一步工作而非顺手改 |
| **检索语料小、评测集小** | 151 条语料 + 20 条 query、单标注人。真实上线前要扩到 100+ query 并做双人标注一致性 |
| **无 multi-agent 编排** | 单循环 + `CRITIC_REVIEW` 阶段，不是多角色协作。要扩的话会把 critic 拆成独立 agent，返回结构化裁决（可测、可回放），而不是让两个 agent 自由对话 |
| **真实模型指标不稳定** | 模型与温度一变指标就变，所以只报「模型 + 参数 + 用例数」三件套，不承诺单一数字 |
| **本地单机，无服务端** | 没有多用户、并发、配额这些服务端问题；数据全在本机 `db.json` |
| **渲染层无框架** | 纯 DOM + 手写 diff-free 重渲染，页面大时性能靠分页与增量更新，不是虚拟 DOM |
