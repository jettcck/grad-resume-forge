# 投递地点与距离（校园招聘场景）

> 场景：在招聘平台上投了一家公司，却不知道它离自己学校有多远。
> 这个功能把「每家公司 ↔ 出发地」的**直线距离**算出来，按由近到远排好，并画成相对位置图。

## 一、分成两层，默认零联网

| 层 | 是否联网 | 说明 |
|---|---|---|
| **离线距离对比**（默认，永远可用） | 不联网 | 内置城市/区县坐标表 + 大圆距离（Haversine），纯本地计算。出图是自绘 SVG：以出发地为原点的相对位置散点图 + 距离条形排序 |
| **在线地图**（可选，默认关闭） | 开启后才联网 | 真实地图瓦片，用来核对具体位置；并可直接在地图上点选，把出发地或某家公司定到精确坐标 |

**开启在线地图前，应用不发起任何地图相关网络请求。**

## 二、为什么瓦片要绕一层主进程

直觉做法是让渲染层直接 `<img src="https://tile...">`，但那要求把瓦片域名写进 `img-src`；
一旦支持用户自定义瓦片源，就得放宽成 `img-src https:` —— 等于把上一轮刚收紧的边界重新打开。

所以改成：**主进程取瓦片 → 以 `data:` URL 交给渲染层**。

- CSP **一行都不用改**（`data:` 本来就在 `default-src` 里）
- 渲染层继续待在沙箱里，仍然不需要任何网络能力
- 代价：这一段成了唯一「能主动联网」的组件，因此 SSRF 防护必须自己做

### 主进程侧的安全约束（`src/main/tile-proxy.ts`）

| 约束 | 为什么 |
|---|---|
| 只允许 `https` | 明文 HTTP 会被中间人改写瓦片内容 |
| 主机名不得是内网/回环/链路本地/保留地址 | 否则应用就成了「能读内网 HTTP 服务的工具」：`127.0.0.1` 的管理口、`192.168.x` 的路由器、云元数据 `169.254.169.254` 都能被探测 |
| **每一跳跳转都重新校验** | 否则一个 `302` 到内网就绕过了上面两条 |
| 限制跳转次数、超时、单块体积（512KB） | 防呆 + 防被喂大文件 |
| 内容类型必须是 `image/*` | 防止把登录页 / JSON 当瓦片塞给渲染层 |
| 磁盘缓存 + 上限 3000 块 | 少重复请求（对瓦片服务礼貌），同一片区域第二次打开不再联网 |
| 不回传 URL 模板给渲染层 | 模板里可能带用户自己的 key |

这些都有测试守着（见第五节），其中「302 跳转到 `169.254.169.254` 必须被拦下」是专门写的一条。

## 三、坐标这块最容易「看起来对、其实错」

### 1. 坐标系：内部统一 WGS-84

内置坐标表的原始数据（[88250/city-geo](https://github.com/88250/city-geo)，木兰宽松许可证 v2）
由百度地图 API 补齐。经参照点核对，其偏移量（例如北京东城区约 `+0.0063°/+0.0064°`）
明显小于 BD-09 所需量级（约 `+0.011°/+0.0126°`），符合 **GCJ-02** 特征，
因此构建期用标准算法把它转成了 **WGS-84**，使全应用只有一种内部坐标系。

校核（转换后 vs 权威 WGS-84 地标）：

| 城市 | 偏差 | 城市 | 偏差 |
|---|---|---|---|
| 北京 | 0.9km | 乌鲁木齐 | 0.6km |
| 上海 | 0.9km | 三亚 | 0.9km |
| 广州 | 1.0km | 杭州 | 5.8km |
| 深圳 | 0.8km | 哈尔滨 | 10.0km |
| 成都 | 1.3km | 拉萨 | 5.1km |

后三者偏差大不是坐标错了，而是那三个城市的政府驻地离所选地标本身就有那么远
（例如哈尔滨市政府在松北区，距市中心约 10km）。

**显示到地图上时才按瓦片源的坐标系换算**：OSM 是 WGS-84，高德是 GCJ-02。
不换算的话，同一个点在高德底图上会整体偏移约 500m。

**港澳台单独排除**：它们落在中国大陆的经纬度包围盒内，但官方制图用 WGS-84、
并不施加 GCJ-02 偏移。照搬「在中国境内就偏移」会给香港的坐标平白加 555m ——
正好卡在「肉眼能看出来、又不至于让距离结论出错」的位置。

### 2. 精度口径（界面上也这么写）

- 城市级点多为**政府驻地或城区质心**，与「你要去的那栋楼」差 5–10km 很常见
- 区级点误差通常 1–3km
- 需要精确位置时：在地图上点选，或手动填经纬度
- 内置表覆盖 **344 个城市 + 2966 个区县**（港澳台手工补齐）

### 3. 位置文本解析

招聘平台上抄下来的写法五花八门，所以解析要能容忍：

| 输入 | 解析结果 |
|---|---|
| `北京·朝阳区` / `北京市朝阳区` | 北京 \| 朝阳（区级） |
| `上海·浦东新区` | 上海 \| 浦东 |
| `广东深圳南山区科技园` | 深圳 \| 南山 |
| `杭州` / `杭州市` | 杭州（城市级） |
| `成都市高新区` | 成都（"高新区"不是行政区，降级到城市级，不硬猜） |
| `海南藏族自治州` | 海南藏族（长键优先，不被"海南"抢走） |
| `某个不存在的城市` | `null` —— 由界面提示手填，**不硬猜** |

## 四、数据与接口

- **出发地**（学校/住处）：存在设置键 `map` 里，**按账号隔离**（`USER_SCOPED_SETTINGS`）
  ```json
  { "origin": { "label": "我的学校", "lat": 30.27, "lng": 120.15, "source": "city|district|manual|map", "level": "city|district" } }
  ```
- **公司位置**：存在投递记录上（`Application.place / lat / lng / placeSource`），
  手工填的坐标优先于 `place` 的查表结果。字段是展开透传进 store 的，老记录不受影响。
- **IPC**：`map:sources` / `map:tile` / `map:cacheStats` / `map:clearCache` / `map:setCustomSource`
  （`map:tile` 不接受任意 URL，只接受"瓦片源 id + z/x/y"）

> 途中修掉一个真实缺陷：`settings:save` 对非 `agent` 键没有传 `userId`。
> `map` 一旦设为用户级，读会按账号、写却落到全局键上——出发地根本存不住。
> 现在两者都带 `userId`，且 `test-e2e.js` 有断言守着「没有写到全局 map 键上」。

## 六、已知限制（不假装没有）

- **是直线距离，不是通勤时间**。界面上如实标注；想算通勤需要路径规划 API，那要联网且多半要 key。
- **没有自动抓取招聘平台**。公司所在地需要用户填一次（从平台上抄，或点"一键直投"时按总部预填）。
  自动抓取第三方平台既不合法也不稳定。
- **"一键直投"预填的是总部城市**，同一岗位挂在别的城市时用户要自己改。
- **高德瓦片是面向网页的公开服务，不是官方开放 API**，仅供个人低频查看；界面上已注明。
- 城市与区县坐标是**近似值**，见第三节的精度口径。
