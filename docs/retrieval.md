# 检索层：BM25 / 向量 / RRF 的实测对比

> 语料 151 条客观题，20 条人工标注 query，四种方案实测结果。
> 复现：`node evals/retrieval-eval.js --no-vector`（只跑 BM25）或
> `node evals/retrieval-eval.js --model bge-m3`（需 Ollama）。
> 代码：`packages/retrieval/src/index.ts`（零第三方依赖）。

---

## 1. 为什么自己写，不引向量库

语料规模决定架构。这个项目的检索语料是：

| 用途 | 规模 |
|---|---|
| 客观题（题干+选项+解析+标签） | 151 条 |
| 编程题（题面+IO+用例提示） | 43 条 |
| 简历要点 | 每人几十条 |

**十万条以下的暴力检索是毫秒级**，引向量库只会带来三个成本：部署依赖、索引更新逻辑、调参空间。
所以这里只做两件事：一个 BM25 索引 + 一个余弦暴力扫描。

**什么时候该上向量库**：粗算一下——768 维 float32 单条 3KB，10 万条是 300MB，
暴力扫描 10 万 × 768 ≈ 7700 万次乘加，单核约 50–80ms，已经开始影响交互；
到 50 万条就是 400ms 级，必须上 ANN（HNSW）。**临界点我定在 10 万条**。

## 2. 分词：中文是绕不过去的坑

BM25 依赖词项匹配，而中文没有空格。三种选择：

| 方案 | 代价 | 本项目选择 |
|---|---|---|
| 引 jieba / nodejieba | 增加原生依赖，打包体积与跨平台编译成本 | ❌ |
| 单字切分 | 召回高但噪声大（「的」「是」全是词） | ❌ |
| **bigram** | 会产生「并高」这类无意义组合 | ✅ |

bigram 把「高并发」切成「高并 / 并发」，不需要词典，召回比单字精确。
无意义组合由 BM25 的 IDF 自然压低（它们在语料里 df 很低，但也不出现在 query 里）。

英文与数字单独处理：`c++`、`node.js`、`c#` 这类技术栈写法要能整体匹配，
所以用 `[a-z0-9][a-z0-9_+#.-]*` 抽，再削掉尾部的点。

## 3. 评测怎么设计（避免自证）

**query 来源**：模拟真实场景的自然语言，不是关键词堆砌。分两组：

- **keyword（8 条）**：用词与题库高度重合，BM25 应该强
  > 「MySQL 索引在什么情况下会失效」
- **semantic（12 条）**：用工作场景描述，需要同义理解
  > 「两个人同时修改同一条记录，后提交的把先提交的覆盖了，数据库层面怎么避免」

**期望答案怎么标**：逐题核对题干后人工确认「语义上真正相关」的题 id。
**不是**用检索器跑一遍再把它召回的当答案（那等于自证）。

**指标**：
- `hit@k`：top-k 里是否命中任一期望题。对「找相关材料」这类任务，它比 precision 更贴切——用户只需要看到一条对的。
- `MRR`：第一个命中项的排名倒数均值，衡量「排得够不够前」。

评测集在 `evals/retrieval-cases.json`，20 条，可增补。

## 4. 实测结果

语料 151 条 · 查询 20 条 · 2026-10-22 本机实测

| 方案 | hit@1 | hit@3 | hit@5 | MRR | 单查询延迟 |
|---|---|---|---|---|---|
| BM25（bigram） | 60.0% | 65.0% | 80.0% | 0.649 | **0.20ms** |
| 向量 · nomic-embed-text | 40.0% | 50.0% | 50.0% | 0.450 | 0.50ms |
| **向量 · bge-m3** | **75.0%** | **80.0%** | **85.0%** | **0.785** | 0.50ms |
| RRF 融合（BM25 + bge-m3, k=60） | 70.0% | 80.0% | 85.0% | 0.762 | 0.70ms |

按类型拆开看，差异更清楚：

| 方案 | keyword hit@3 | semantic hit@3 |
|---|---|---|
| BM25 | 87.5% | 50.0% |
| 向量 · nomic-embed-text | 87.5% | 25.0% |
| **向量 · bge-m3** | **100%** | **66.7%** |
| RRF 融合 | 100% | 66.7% |

建索引成本：BM25 7ms（纯 CPU）；embedding 151 条 bge-m3 约 3.6s（本机 CPU，只需一次，结果可缓存）。

## 5. 三个结论

### 5.1 中文语料上，模型选择的影响远大于架构选择

同一套代码、同一份语料，只换 embedding 模型：

- nomic-embed-text：hit@3 **50%**（semantic 只有 25%）
- bge-m3：hit@3 **80%**（semantic 66.7%）

差 **30 个百分点**。诊断过程：nomic 对「热点数据突然失效，瞬时大量请求打到数据库」召回的
top-1 是「有序数组中求两数之和」——它没有理解中文长句的语义，只是在做向量空间里的近邻。

**教训**：检索效果差时先怀疑模型，再怀疑架构。我当时差点去调 BM25 的参数、加字段权重，
实际问题是模型选错了。

### 5.2 融合不是银弹：两路能力差距大时，融合会拉低上限

RRF 融合（BM25 + bge-m3）的 hit@3 是 80%，与纯 bge-m3 持平；MRR 0.762 < 0.785，**反而略低**。

原因：BM25 在 semantic 组只有 50%，RRF 把它的排名也计入融合分，
等于用一个弱模型的判断去稀释强模型的判断。

**结论**：RRF 的价值在**鲁棒性**（某一路在某类 query 上失效时兜底），
不在「必然提升精度」。两路水平接近时融合有效；差距大时应该**先淘汰弱的那一路**。

### 5.3 BM25 仍是必须保留的基线

bge-m3 在 keyword 组拿到 100%，看起来 BM25 可以扔了。但：

- BM25 建索引 7ms、查询 0.2ms、零依赖、可解释（能说清「因为命中了 索引 + 失效」）
- embedding 需要模型文件（bge-m3 是 1.16GB）与一次 3.6s 的预热
- 无模型环境下（用户没装 Ollama）BM25 是唯一可用方案

所以最终形态是 **BM25 兜底 + 有模型时用向量**，而不是二选一。

## 7. 已知局限

| 局限 | 说明 |
|---|---|
| 评测集只有 20 条 | 单标注人、单一语料。真实上线前应扩到 100+ 条并做双人标注一致性检查 |
| expect 单值标注 | 有些 query 有多个合理相关题，这里只标了 1–2 个，会低估实际召回 |
| 只测了检索，没测下游 | 「召回的题是否真的更适合组卷」需要单独评（比如对比两组卷子的知识点覆盖与难度分布） |
| bge-m3 在 CPU 上做 embedding | 151 条约 3.6s。如果语料涨到几千条，需要 GPU 或改用更小的中文模型 |
| 没有做 query 改写 | 用 LLM 把 JD 拆成多个子 query 再检索，通常还能提升几个点，但会引入延迟与成本，未做 |
