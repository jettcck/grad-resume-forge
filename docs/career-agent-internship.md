## 0. 结论先行

**你的定位**：不是"用过 LangChain 做过 demo"的候选人，而是**独立设计并实现过可控 Agent Runtime、且有评测体系与质量门禁**的工程型候选人。这在实习池里是稀缺的。

**最强证据**（三件，面试时优先讲）：
1. `packages/agent-core` 把 Agent 运行时从业务里剥出来，**11 状态机 + 允许转移表 + 工具契约 + 四项预算 + 取消/回放**，能脱离 Electron 用假领域测试（52 条断言）。
2. `evals/agent-bench.js` **65 个任务用例、9 类场景**，mock 层确定性评测进 CI，有**双口径指标**（行为符合预期 100% vs 业务完成率 63.1%）和**质量门禁**。
3. **改写通过率 87.2% / 数字保全率 100% / 编造技能率 0%** —— 防幻觉不是靠 prompt 求它别编，是靠校验门 + 注入攻击用例验证的。

**最大缺口**（补强优先级见 §6）：
- ~~没有 RAG~~ → **已补**（2026-10-22）：自建 BM25/向量/RRF，20 条标注评测，bge-m3 hit@3 80%
- **没有 multi-agent 编排**（单循环 + critic 阶段，不是多角色协作）
- **没有真实模型的量化评测**（LLM 层只有链路自测，数字明确标注"不要引用"）

这三条恰好是 Agent 岗 JD 的高频词。**缺口不可怕，讲清楚"我知道缺什么、为什么没做、补起来会怎么做"反而加分**；装作有才是致命的。

### ⚠️ 需要改写措辞（否则面试被追问会翻车）

| 原始说法 | 问题 | 改成 |
|---|---|---|
| "业务完成率 63.1%" | 听起来像"Agent 只有六成功率" | "双口径评测：行为符合预期 100%、业务完成率 63.1%（失败样本按设计不完成）" |
| "工具成功率 89.3%" | 会被问"为什么不是 100" | "干净路径 100%，含注入场景 89.3%（bad_args/unknown_tool 为故意失败）" |
| "JD 覆盖率提升 0 个百分点" | 像 bug | **主动讲**："这是设计结论：防幻觉门禁止写入档案里没有的技能，所以风格层改写不该提升覆盖率" |
| "支持 3 种语言判题" | 平淡 | "3 语言编译执行链路（g++ -std=c++17 -static / Python / Node），含 CE 报错回传与 Defender 误杀重试" |

### ❌ 不能说的（诚实边界）

- **"服务了 N 个用户 / 日均调用 N 次"** —— 本地单机桌面应用，没有服务端，没有用户数据。编了必翻车。
- **"模型准确率 95%"** —— LLM 层只有链路自测，文档明确写"数字不要引用"。
- ~~"RAG 检索增强"~~ —— 现在**可以讲**，但要讲对：你写的是自建 BM25 + 向量，不是"接了个向量库"；被问"用的什么向量库"要答"没用，151 条语料暴力余弦 0.5ms"。
- **"多 Agent 协作"** —— 是单循环 + critic 阶段，不是多角色编排。可以说"有 critic 复核阶段"，不能说 multi-agent。

## 4. 简历条目改写示例（可直接替换）

### 示例 1：Agent 运行时（核心条目）

**改前**（常见但弱）：
> 使用 LLM 开发简历优化 Agent，支持多轮改写与工具调用，提升简历质量。

**改后**：
> **可控 Agent Runtime（独立 npm 包，1,109 行，零 Electron 依赖）**
> · 设计 11 状态机（CREATED→ANALYZING_JD→PLANNING→EXECUTING_TOOLS→VALIDATING→CRITIC_REVIEW→COMPLETED + 4 终态），用**允许转移表**约束推进，非法转移直接抛错——开发期即拦截过一次 `VALIDATING→COMPLETED` 漏配导致的整次运行判失败
> · 工具契约层：6 个工具统一声明 `inputSchema / permission(readonly|write) / timeoutMs / maxRetries / idempotent`；**仅幂等工具自动重试**，非幂等写操作宁可失败交上层决策
> · 四项预算（maxSteps / maxToolCalls / maxDurationMs / maxTokens）+ AbortSignal 在工具间**安全点**取消，状态记 CANCELLED 且**保留已完成改写**
> · 拆分标准可验证：core 在无 Electron、无业务数据的假领域下跑通 **52 条断言**

### 示例 2：评测体系（最加分条目）

**改前**：
> 编写单元测试保证 Agent 稳定性。

**改后**：
> **Agent 评测体系（65 用例 / 9 类场景 / 质量门禁进 CI）**
> · 用真实 `agenticLoop` + 真实校验门，只把模型换成脚本化 mock：确定性、零成本、可进 CI
> · 场景设计覆盖 happy / no_analysis / lazy / partial / all_rejected / bad_args / unknown_tool / **injection** / 长文与空档案
> · **双口径指标**修正了上一版的乐观偏差（原先把"没分析 JD 却有一条改写"期望成 ok=true）：行为符合预期 100%、业务完成率 63.1%
> · 门禁：干净路径工具成功率 100%、数字保全率 100%、编造技能率 0%（注入用例守护）；断言"每个用例失败次数**恰好等于**注入次数"，多一次少一次都算回归
> · 实测：改写通过率 87.2%（143 通过 / 21 拒收）、运行时开销 1.7ms

### 示例 3：可观测与隐私（差异化）

**改后**：
> **Agent 运行记录与脱敏（白名单式，非截断）**
> · 每条 run 记录 `runId / status / currentStep / budget / usage / trace`，trace 逐步记 tool / 入出参摘要 / latencyMs / retryCount / tokens / errorType
> · 入参与**出参摘要走同一规则**（只脱敏入参不足以防泄漏）：超 12 字的字符串替换为 `{len, digest}`，条目 id 与工具名等短标签保留——落盘后仍可用于复盘
> · 阈值由测试反推：24 字版本被一条 18 字改写用例证伪（真实要点 15–40 字），收紧到 12 字
> · 默认不存原文，回放如实报告"有 N 步因未保存入参被跳过"，而非用占位对象跑出假错误

### 示例 4：工程兜底（体现"真跑过"）

**改后**：
> **跨语言判题沙箱（43 题 × JS/Python/C++，207 条断言）**
> · 编译一次多用例复用；超时/超限 `taskkill /T /F` 杀进程树防孤儿进程；输出 64KB 截断判 OLE

## 6. 补强路线（按 ROI 排序，含验收标准）

### P0 · 真实模型层评测（1 天，收益最高）— 🟡 部分完成

**为什么**：你现在所有 Agent 指标都是 mock 层的。面试官一定会问"真实模型效果如何"，答"没测"会丢掉最关键的分数。

**已完成（2026-10-22 实测）**：

| 项 | 结果 |
|---|---|
| 评测链路 | ✅ 打通：`agent-bench-llm.js` 接 Ollama OpenAI 兼容端点，3/3 请求成功返回、指标正常汇总 |
| 1.5B 模型（qwen2.5:1.5b，986MB） | ✅ 已拉取并跑出结论：**任务完成率 0%，全程不产生 `tool_calls`**（空 content + `finish_reason=stop`） |
| 端点能力核验 | ✅ 同一端点普通对话正常、带 `tools` 参数返回 200 —— 证明是模型不调工具，不是协议不通 |
| 7B 模型（qwen2.5:7b，4.7GB） | ❌ 未完成：本机沙箱单命令有时长上限，且 Ollama blob 中断后丢弃分片从头重下（实测 2.08GB → 0.97GB 回落） |

**这个负结果本身可以直接用**（面试价值不低于正向指标）：

> "我把评测接到真实模型上，用 qwen2.5:1.5b 跑，完成率 0%——但不是框架问题：同一端点普通对话正常、tools 参数返回 200，只是模型不产生 tool_calls。这量化了 Agent 任务对模型规模的下限。7B 的指标我还没拿到，因为本机下载被中断，不是代码问题。"

**还差一步（在正常网络下 30–45 分钟）**：
```bash
ollama pull qwen2.5:7b          # 必须一次连续拉完，中断会重下
set AGENT_BENCH_ENDPOINT=http://127.0.0.1:11434/v1
set AGENT_BENCH_MODEL=qwen2.5:7b
node evals/agent-bench-llm.js --sample 20
```
记录：任务完成率、平均步数、平均 token、平均延迟、失败分类，并标注 `模型 / 温度 / 用例数` 三件套。

**验收**：能说出"7B 小模型在 X 类场景下的完成率是 Y%，主要失败模式是 Z"——这句话在面试里的分量超过任何形容词。

**注意**：不要吹大模型指标。7B 小模型的真实数字（哪怕完成率只有 40%）配上"失败模式分析"远比"95% 准确率"可信。

### P1 · 最小 RAG（2–3 天）— ✅ 已完成（2026-10-22）

**成果**：`packages/retrieval`（零依赖）+ `evals/retrieval-eval.js` + `docs/retrieval.md`

| 方案 | hit@3（全部） | keyword 组 | semantic 组 | MRR |
|---|---|---|---|---|
| BM25（中文 bigram） | 65.0% | 87.5% | 50.0% | 0.649 |
| 向量 · nomic-embed-text | 50.0% | 87.5% | 25.0% | 0.450 |
| **向量 · bge-m3** | **80.0%** | **100%** | **66.7%** | **0.785** |
| RRF 融合（BM25 + bge-m3） | 80.0% | 100% | 66.7% | 0.762 |

**三个可直接讲的结论**：
1. **模型选择的影响 > 架构选择**：同代码同语料，换 embedding 模型 hit@3 从 50% → 80%。诊断过程能讲（nomic 把「热点数据失效」召回成「有序数组两数之和」）。
2. **RRF 不是银弹**：融合后 MRR 0.762 < 纯 bge-m3 0.785——弱路稀释强路。**融合价值在鲁棒性，不在必然提升**。
3. **BM25 必须保留**：7ms 建索引、0.2ms 查询、零依赖、可解释，是无模型环境的唯一方案。

**能回答的追问**：
- 为什么不用向量库 → 151 条语料暴力余弦 0.5ms；临界点测算：10 万条约 50–80ms，50 万条必须上 HNSW
- chunk 怎么切 → 本场景是结构化短文本，一题一 chunk，不做切分；切分只对长文档有意义
- recall@3 多少 → 用 hit@3 而非 recall（单相关文档场景两者等价），数字见上表
- 为什么融合没赢 → 见结论 2，这是实测不是推测

### P2 · 工具调用的结构化输出加固（1 天）

**为什么**：你已有 `bad_args` 用例，但没有"模型给错 JSON → 自动修复重试"的闭环。这是生产级 Agent 的必备。

**做什么**：
- 工具入参用 JSON Schema 校验（不只是手写 `inputSchema`）
- 校验失败 → 把**结构化错误信息**回灌给模型（`{"error": "field X expected string, got number"}`）→ 允许 1 次自修复重试
- 加一个 `schema_repair` 评测类别（模型故意给错 → 是否修复成功）

**验收**：`bad_args` 场景下从"拦下并继续"升级为"拦下 → 回灌 → 修复成功率 X%"。

### P3 · 多 Agent 的最小形态（3–5 天，可选）

**为什么**：不是必需，但能把"critic 阶段"升级成真正的多角色。

**做什么**：把现有 `CRITIC_REVIEW` 拆成独立 agent（独立 prompt + 独立工具集 + 独立预算），主 agent 把候选交给 critic，critic 返回结构化裁决（`{accept, reasons[], severity}`）。**不要做成自由对话的多 agent**——那是最容易失控的形态。

**验收**：能讲清"为什么用结构化裁决而不是让两个 agent 对话"（可测、可回放、成本可控）。

### P4 · Prompt 版本管理（半天）

### Demo 脚本（录屏 90 秒，按这个顺序）

1. **0–15s**：打开应用 → 选示例档案 → 点"Agent 优化"（展示实时步骤轨迹：analyze_jd → audit → rewrite → validate → critic）
2. **15–35s**：故意点"取消" → 展示状态变 CANCELLED 且**已完成的改写保留**
3. **35–55s**：打开"关于 → 最近运行记录" → 展开 trace（latency / retry / tokens / 拒收原因）
4. **55–70s**：切到笔试中心 → 编程题 → 选 C++ → 写一个错误答案 → 展示 WA 用例对比
5. **70–90s**：终端跑 `node evals/agent-bench.js` → 65 用例、门禁全绿

**为什么这个顺序**：先给"能跑"，再给"可控"（取消/保留），再给"可观测"（trace），最后给"可验证"（评测）。这四层正好对应 Agent 岗的四项核心要求。

### 面试讲述顺序（3 分钟版）

1. **问题**：简历改写的 Agent 容易"编造技能"和"改坏数字"，而且出了问题查不到原因。
2. **做法**：把 runtime 抽出来做成状态机 + 工具契约，把"能不能写"交给校验门而不是 prompt。
3. **验证**：65 用例 9 类场景，注入攻击用例专门测编造，编造率 0%。
4. **踩坑**（选一个讲透）：脱敏阈值 24→12 被自己的测试证伪 / 状态机漏配转移导致整次运行失败。
5. **边界**：检索做了但没接进组卷、没做多 Agent，说明原因与补法。
