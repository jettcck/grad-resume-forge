# 检索评测：从 20 条到 62 条，从单一指标到区间

## 1. 为什么重做

v1 只有 20 条 query、一个 hit@3，结论写出来是「hit@3 = 80%」。
这个数字有两个问题：

- **样本太小的比例不可当结论。** 20 条里错 4 条就是 80%，错 5 条就是 75%。
  不给区间的百分比会被读成稳定性能。
- **只测「找得到」，没测「找不到时会不会硬凑」。** RAG 最典型的翻车不是漏召回，
  而是把不相关材料塞进上下文，让模型拿它当依据去编。

v2 要回答的是：在什么范围内、以多大把握、能说清哪个结论。

## 2. 查询集怎么构造

`evals/retrieval-cases-v2.json`，62 条，5 类：

| 类型 | 条数 | 构造方式 | 想暴露的问题 |
|---|---:|---|---|
| keyword | 14 | 关键词与题库用词直接重合 | 基线能力 |
| paraphrase | 18 | 同义改写，不共用关键术语 | 纯词匹配的天花板 |
| colloquial | 12 | 口语、省略、短句 | 真实用户提问形态 |
| multi_hop | 10 | 一句话问两个考点 | 单文档是否够用 |
| out_of_domain | 8 | 语料里根本没有答案 | 会不会硬凑结果 |

标注纪律（写在文件里，供复核）：

- 逐条核对题干后标注，**不是**用检索器反查再当答案（反查等于自证）。
- 分级相关度：`grade=2` 直接回答，`grade=1` 同考点但只部分相关。
- `out_of_domain` 的 relevance 必须为空；非 OOD 必须非空。
- 评测脚本会先校验：id 是否存在语料、grade 是否合法、类型与 relevance 是否自相矛盾。
  标注写错时直接报错退出，不让它静默变成 0 分。

## 3. 指标

| 指标 | 定义 | 为什么需要 |
|---|---|---|
| Hit@1/3/5 | top-k 里是否出现任意相关文档 | 最贴近「有没有把材料递到手上」 |
| Recall@5 | top-5 中相关文档数 / 全部相关文档数 | 多相关文档时，命中一个不代表够用 |
| MRR@10 | 第一个相关文档排名倒数 | 衡量「排得够不够前」 |
| nDCG@5 | 分级相关度的折损累计增益 | 区分 grade 2 和 grade 1 |
| 语料外误召回率 | OOD 查询中返回了结果的占比 | 硬凑材料的直接度量 |
| p50 / p95 延迟 | 单次检索耗时 | 说明成本 |

每个主要指标附 **bootstrap 95% 置信区间**（1000 次重采样，固定种子 20261028）。
固定种子是为了「同一条命令跑两次得到同一组区间」，否则区间抖动会被误读成系统变化。

## 4. 结果（2026-10-28 实测，BM25）

语料 151 条题库，54 条有标注 query（不含 8 条 OOD）：

| 指标 | 值 |
|---|---:|
| Hit@1 | 79.6% |
| Hit@3 | 85.2%（95% CI 75.9%–92.6%） |
| Hit@5 | 92.6% |
| Recall@5 | 91.7% |
| MRR@10 | 0.835 |
| nDCG@5 | 0.836（95% CI 0.757–0.908） |
| 延迟 p50 / p95 | 0.08 ms / 0.48 ms |

分类别看，差距比总均值更有信息量：

| 类型 | n | Hit@3 | nDCG@5 |
|---|---:|---:|---:|
| keyword | 14 | 92.9% | 0.956 |
| colloquial | 12 | 91.7% | 0.922 |
| multi_hop | 10 | 100% | 0.890 |
| paraphrase | 18 | **66.7%** | **0.657** |

结论要分两层说：

1. 关键词能对上时，BM25 在这个语料上够用（92.9%）。
2. 需要同义理解时掉到 66.7%，这才是语义检索的价值区间 —— 也是当前最大的短板。

multi_hop 100% 属于「题目本身关键词多」带来的，不代表它能做多跳推理，不要过度解读。

## 5. 关键发现：语料外问题会硬凑

8 条语料外问题里，**6 条仍然返回了结果（75%）**。

原因不是「召回了相似内容」，而是 BM25 的机制缺陷：
只要命中任意一个词就计分，而分数又被极罕见词（df=1）的 IDF 放大。
例如「红烧肉怎么做才不腻」只撞上「怎么」「么做」两个词，却因为「么做」在语料里只出现一次，拿到 8.5 分。

这在 RAG 里是危险的：Agent 拿到的「材料」看起来有分数、有排名，实际与问题无关，
而模型并不知道这是噪声。

### 阈值扫描

在 62 条 query 上扫了三类阈值（完整表在 `benchmarks/retrieval-report.json` 的 `thresholdSweep`）：

| 配置 | Hit@3 | nDCG@5 | 语料外误召回 |
|---|---:|---:|---:|
| 不设阈值 | 85.2% | 0.836 | 75.0% |
| minScore=5 | 83.3% | 0.827 | **37.5%** |
| 覆盖率 ≥ 0.2 | 74.1% | 0.712 | 25.0% |
| 覆盖率 ≥ 0.4 | 38.9% | 0.356 | 0% |

选择规则写进了脚本，可复核：**在 Hit@3 相对基线下降不超过 2pt 的前提下，取误召回最低的配置**。
按这条规则选中 `minScore=5`：用 1.9pt 的召回换掉一半误召回。

覆盖率阈值更干净（能压到 0%），代价是 Hit@3 掉到 38.9% —— 这个交换比不划算，
所以没有采用，但数字留在报告里，方便以后语料变大时重新比较。

### 产品侧的落地

`src/main/retrieval.ts` 的 Agent 工具使用 `minScore=5`，并有回归测试守住：

```text
语料外问题至少压掉一半（实测 5/8，阈值前为 2/8）
阈值没有误伤正常查询
```

同时 `prompts/agentic-system-v2.txt` 明确写：检索结果是辅助材料，不是用户档案证据，
不得写成用户本人经历。这两条合起来才算把「检索污染」这条路堵住。

## 6. 向量层：本次未测，不编数字

本机 Ollama 只有生成模型（qwen3:8b / deepseek-r1:8b / gemma4:26b），没有 embedding 模型。
评测脚本对 `nomic-embed-text` 做可用性检查，结果是不可用，于是明确跳过：

```json
"vector": { "attempted": true, "available": false, "model": "nomic-embed-text" }
```

拉取 `bge-m3` 与 `nomic-embed-text` 均因网络超时失败（各 10 分钟无响应）。
因此本报告里**没有任何向量或融合数字**。要补齐，先准备模型再重跑：

```bash
ollama pull nomic-embed-text
node evals/retrieval-eval.js            # 会自动跑 BM25 / 向量 / RRF 三路并写报告
node evals/retrieval-eval.js --model bge-m3
```

评测协议已经就位（同一批 query、同一语料、同一 top-k、同一指标与区间），
模型到位后可以直接得出可比的结论，不需要改代码。

## 7. 局限

- **语料只有 151 条**，且集中在题库。这个规模下的延迟数字（0.08ms）没有工程参考价值，
  不能用来推生产性能。
- **62 条 query 仍然偏小**：Hit@3 的 95% 区间宽 16.7pt。写成「85.2%」时必须带区间。
- **单标注人**：没有第二人复核，标注意见分歧无法量化（没有 inter-annotator agreement）。
- **OOD 只有 8 条**：37.5% 的误召回率，其区间可能从 10% 到 70%，只能当方向性结论。
- **没有端到端验证**：本次没有测「检索结果对最终改写质量的影响」。
  真实模型在本机单次 30–190 秒，做一个 4 用例 × 2 组（none / bm25）的对照要十几分钟，
  属于下一步而不是本次范围。

## 8. 简历措辞

可以写：

> 自建 62 条分层检索评测集（关键词 / 同义改写 / 口语 / 多跳 / 语料外），
> 实现 Hit@K、Recall@K、MRR、nDCG@5 与 bootstrap 置信区间；
> 在 151 条题库语料上测得 BM25 Hit@3 85.2%（95% CI 75.9–92.6），
> 并定位「同义改写仅 66.7%」与「语料外误召回 75%」两个短板；
> 按代价比扫描阈值，将误召回降到 37.5% 而召回仅降 1.9pt。

不要写：

- 「RAG 召回率 85%」——必须带语料规模与区间
- 「支持大规模知识库」——只有 151 条
- 「向量检索效果优于 BM25」——本次没有向量数据
